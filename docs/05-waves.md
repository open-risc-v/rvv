> 本文是 **8 人 × 24 个月**的人工基线，**工作量（人日）仍以此为准**。

## 3. 为什么是这个顺序（四条硬约束）

1. **W0 必须最先，且必须是"公共方案"**：分派、`vsetqvl` 循环写法、probe、paired 基准、
   毒化矩阵如果每个包各写一遍，48 个项目会多花 60–100 人日，且结果不可比。
2. **W1 先于 W2**：W1 的六个包上游已有 RVV，能把 A/B、真机、CI 三条链路在低风险项目上跑通。
   等 W2 的 libvpx 上再发现 CI 有问题，代价是几周的返工。
3. **W2 内部按"解码优先"**：解码必须位精确、且是消费端必经；编码（x264/x265）可以容忍，
   放到后面。`ffmpeg` 放最后是因为它要把前面所有 codec 的成果集成起来。
4. **W6 依赖全部前置**：chromium 自身的 RVV 工作量主要在 Skia/V8/ANGLE，但它同时**消费**
   libpng/zlib-ng/libjpeg-turbo/libvpx/ffmpeg 的成果。前置没完成就做 chromium，会把
   third_party 的重复实现又抄一遍。

## 5. 里程碑（按"可对外说明"的粒度）

| 里程碑 | 时间 | 判定 |
|---|---|---|
| **M-A 基建可用** | M2 | 任意一个包：`new-project.sh` → `device-test.sh build ab bench` 一条链跑通 |
| **M-B 快赢落地** | M4 | W1 六项 G4；图像解码/压缩/TLS 三条路径有真机加速比 |
| **M-C 视频可用** | M8 | VP9/H.264 解码 G4，1080p 播放功耗/帧率达标 |
| **M-D 音频可用** | M9 | Opus + AEC 在 10ms 帧上不退化 |
| **M-E 安全闭环** | M11 | openssl 缺口补齐，TLS 握手/批量加解密加速比达标 |
| **M-F 科学计算** | M14 | Eigen GEMM 达到同频 AVX2 的 70%；FFTW 达到自身 SSE 版的 60% |
| **M-G 平台集成** | M20 | Chromium 在目标机上启动/渲染/视频三条基线不劣化，关键路径加速比可测 |
| **M-H 收尾** | M24 | 在册项目 G4 比例 ≥80%，上游化 ≥50% |

## 6. 排期风险与应对

| 风险 | 触发信号 | 应对 |
|---|---|---|
| 工具链代码生成不达标（gcc 对某类 intrinsics 生成差代码） | 内核写对了但真机无加速 | 先 probe 再写；必要时落 `.S`；对照 clang |
| 上游大版本变更导致 rebase | 子模块 pin 落后 >6 个月 | 每季度统一 rebase 窗口；baseline 与 src 同步升级 |
| 汇编类项目超支（libvpx/x264/hyperscan） | 单项目累计超 `pd_high` 30% | 触发"关键子集"裁剪：只做 top-N 热点，其余标量 |
| 真机不足 | 排队 >1 周 | 扩 X60/X100 板卡；qemu 只做功能回归 |
| 人员流动 | 单项目只有 1 人熟悉 | `docs/rvv-notes.md` 必须每周更新，作为交接文档 |
