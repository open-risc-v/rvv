# 07 AI 算力下的时间轴（60 token/s）

> 本文**替换** `docs/05-waves.md` 的日历部分：05 保留"人日"作为工作量基线（仍是估算的唯一标尺），
> 本文把同一批人日换算成 AI 产出算力下的**真实墙钟**。两者不冲突：人日不变，日历变。
> 重算命令：`python3 scripts/ai-capacity.py --tps 60 --agents 8 --boards 8 --reviewers 2`

## 1. 一句话结论

60 token/s 让"写代码"这一项快了约 20 倍，但**总工期只快 4–5 倍**：核心 48 项从
**24 个月压到约 24 周（2026-11-16 → 2027-05-04）**，主线瓶颈从"人日"变成
**评审席位（人）× 板卡机时**。多加 agent 没有边际收益，多加评审人才有。

## 2. 60 token/s 换算成什么

| 口径 | 数值 |
|---|---|
| 输出速率 | 60 token/s |
| 每小时 | 216,000 token |
| 8 小时（人类工作日） | 1.73 M token |
| 24 小时连续（agent） | 5.18 M token |
| 折算到"写码产出" | 1 人日 ≈ 100k 输出 token（成品约 400 行，其余是思考/工具/回读的放大） |
| 于是 | 1 人日 的**生成**部分 = 100k/216k ≈ 28 分钟 → **17× 速** |

## 3. 三资源模型（全部系数可调）

| 环节 | 占人日 | 折算 | 依据 |
|---|---|---|---|
| 生成（写内核、胶水、文档） | 25% | 100k token/人日，60 tok/s → 0.46 h/人日 | libspeex-rvv 实测：21 内核 29 轮，成品代码占比低 |
| 验证（构建、差分、A/B、基准、毒化矩阵、真机） | 60% | 1.2 机时/人日（含失败重跑） | 同上，验证占 60%；机时是墙钟，不随 token 变快 |
| 评审（门禁、拍板、上游沟通） | 15% | 0.5 人日/人日（AI 先嚼碎证据） | 人的判断不并行、不可 token 化 |

单项目墙钟 ≈ `pd × 0.05 天`（≈1.2 小时/人日，已含 1.5× 返工缓冲），即**1 个 AI 日 ≈ 20 人日**；
其中生成只有 0.46 h/人日，剩下全是验证机时。**这一条决定了压缩比的上限**。

## 4. 总量（含 W0 与长尾）

| 项 | 人日 | 生成 token | 生成机时(agent) | 验证机时(板卡) | 评审人日 |
|---|---|---|---|---|---|
| 核心 48 + W0 | 2618 | 65.5 M | 303 h | 1897 h | 197 |
| 长尾 118（粗档） | 600 | 15.0 M | 69 h | 432 h | 45 |
| **合计** | **3218** | **80.5 M** | **372 h** | **2317 h** | **241** |

读法：
- 80.5 M 输出 token 是**上限预算**（真实会少 20–30%，因为很多轮是重试）；
- 372 agent-h ÷ 8 个 agent = **46.5 小时**——生成侧两天就能干完，**根本不是瓶颈**；
- 2317 板-h ÷ 8 块板 = **12 天**——验证机时也不是瓶颈；
- 241 评审人日 ÷ 2 人 = **121 工作日 ≈ 24 周**——**这才是主线**。

## 8. 敏感性：加什么才有用

| 变量 | 取值 | 主线结束 | 结论 |
|---|---|---|---|
| 评审人 | 1 | 2027-09-22（44 周） | 一个人评审 = 项目白等 7 个月 |
| 评审人 | 2 | 2027-05-04（24 周） | 当前假设 |
| 评审人 | 3 | 2027-03-16（17 周） | 边际收益最大的一档 |
| 评审人 | 4 | 2027-02-16（13 周） | 已到波次串行下限，再加无效 |
| agent 数 | 8 → 16 | 日历几乎不变 | 生成侧只有 372 机时，翻倍无意义 |
| 板卡 | 8 → 4 | 0（仍被评审卡住）| 4 板需 24 天验证，尚未成为瓶颈；降到 2 块才会顶到前面 |
| token 预算 | 50k/100k/200k 人日 | 生成 186/372/744 h | 200k 时 8 agent 也只要 4 天，仍不是瓶颈 |

**若把评审压到只做 G2 / G4 两次**（G1/G3 只收 AI 生成的证据报告）：评审人日 241 → **约 80**，
2 人 → 8 周，主线可到 **2027-03 中旬**。这是唯一还能再省一个月的动作，代价是 G3 阶段的质量靠门禁不靠人。

## 9. 瓶颈转移后的四条硬约束

1. **评审席位是唯一真正稀缺的资源**。48 个项目 × 6 门禁 = 288 次评审，别按"人日"排，
   按"每周能审几个项目"排：2 人满打满算 4 项目/周。
2. **每块板要能跑满 24h**，否则验证机时立刻翻倍。板卡优先级 > agent 数量。
3. **上下文重建成本不可忽略**：每个工程开工都要重读 plan/notes/上游代码，约 50–150k token，
   相当于 6.4 M token 的固定开销（80.5 M 里已含，但换 agent 会重复付）。
   所以**一个项目从头到尾由同一个 agent 会话负责**，不要中途换人。
4. **上游化（G5）不在算力模型内**：PR 提交、reviewer 往返、CI 排队是 8–12 周的日历时间，
   AI 无法压缩。M-H 只能按日历排，不能按 token 排。

## 10. 这个模型最容易错在哪

| 失守点 | 表现 | 纠正 |
|---|---|---|
| 把 60 tok/s 当有效产出 | 按 5.18 M/天 估，得出"一周干完 48 项" | 有效产出系数按 100k/人日 的放大倍数算，别用裸 token |
| 忽略验证机时 | 认为 AI 写完就完事，排期只算生成 | 验证占 60%，且是墙钟，必须按板卡数排 |
| 评审走过场 | 为了赶日历，门禁证据不看就签 | 编造通过比分包更贵：一次错误基线会让下游全部返工 |
| 用 qemu 数字当结论 | 排期按 qemu 加速比乐观 | qemu 只证明功能，性能结论必须真机 |
| 频繁换 agent | 每个波次重开会话，重复装载上下文 | 按项目绑定 agent，上下文成本只付一次 |

## 11. 怎么用

```bash
python3 scripts/ai-capacity.py                        # 默认 60 tok/s / 8 agent / 8 板 / 2 评审
python3 scripts/ai-capacity.py --reviewers 3          # 加一个评审人看能省多久
python3 scripts/ai-capacity.py --tps 30 --boards 4    # 保守场景
# 结果同时写入 data/ai-schedule.csv，plan.xlsx 的「AI 排期」sheet 读它
```
