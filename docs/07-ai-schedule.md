# 07 AI 算力下的时间轴（60 token/s）

> 本文**替换** `docs/05-waves.md` 的日历部分：05 保留"人日"作为工作量基线（估算的唯一标尺），
> 本文把同一批人日换算成 AI 产出算力下的**真实墙钟**。人日不变，日历变。
>
> 两个脚本，一条比一条细：
> - `scripts/ai-capacity.py` —— 波次级，算 token / 机时 / 评审人日（`data/ai-schedule.csv`）
> - `scripts/ai-plan.py` —— **项目级**，把人日摊到具体日期 + agent 槽 + 板卡槽 + 评审队列
>   （`data/ai-plan.csv`，48 行，本文件 §5.5 与 §6 的数据源）

## 1. 结论

60 token/s 让"写代码"快约 **17 倍**，但总工期只快 **4–5 倍**：

- 核心 48 项：**24 个月 → 24 周（2026-11-16 → 2027-05-03）**；
- 真正的稀缺资源是**评审席位**：2 人刚好卡住 24 周，1 人退化成 43 周，3 人降到 17.4 周；
- **agent 只要 3–4 个**（8 个与 3 个的结束日期完全相同）；**板卡 2–4 块**就够，但没有余量；
- 主线结束日期由评审队列决定，不由算力决定。

## 2. 60 token/s 换算成什么

| 口径 | 数值 |
|---|---|
| 输出速率 | 60 token/s |
| 每小时 | 216,000 token |
| 8 小时（人类工作日） | 1.73 M token |
| 24 小时连续（agent） | 5.18 M token |
| 折算基数 | 1 人日 ≈ 100k 输出 token（成品约 400 行，其余是思考、工具调用、日志回读的放大） |
| 于是 | 1 人日 的**生成**部分 ≈ 28 分钟 → 17× 速 |

## 3. 三资源模型（系数全部可调）

| 环节 | 占人日 | 折算 | 依据 |
|---|---|---|---|
| 生成（写内核、胶水、文档） | 25% | 100k token/人日 → 0.46 h/人日 | libspeex-rvv 实测：21 内核 29 轮，成品代码占比低 |
| 验证（构建、差分、A/B、基准、毒化矩阵、真机） | 60% | 1.2 板时/人日（含失败重跑） | 同上，验证占 60%；机时是墙钟，不随 token 变快 |
| 评审（门禁、拍板、上游沟通） | 15% | 0.5 人日/人日（AI 先嚼碎证据） | 人的判断不可 token 化、不可并行 |

单项目墙钟 ≈ `pd × 0.05 天`（≈1.2 小时/人日，含 1.5× 返工缓冲），即 **1 个 AI 日 ≈ 20 人日**。
其中生成只占 0.46 h/人日，**其余全是验证机时**——这条决定了压缩比的上限。

## 4. 总量

| 项 | 人日 | 生成 token | 生成机时(agent) | 验证机时(板卡) | 评审人日 |
|---|---|---|---|---|---|
| 核心 48（项目级排期） | 2558 | 64.0 M | 289 h | 1897 h | 192 |
| W0 基建 | 60 | 1.5 M | 7 h | 43 h | 4.5 |
| 长尾 118（粗档） | 600 | 15.0 M | 69 h | 432 h | 45 |
| **合计** | **3218** | **80.5 M** | **365 h** | **2317 h** | **241** |

读法：生成 365 agent-h ÷ 4 个 agent ≈ **4 天**；验证 2317 板-h ÷ 4 块板 ≈ **24 天**；
评审 241 人日 ÷ 2 人 ≈ **121 工作日 ≈ 24 周**。**只有最后一行是主线。**

三点读法：

## 8. 敏感性（项目级，换参数直接跑脚本）

| 变量 | 取值 | 主线结束 | 结论 |
|---|---|---|---|
| 评审人 | 1 | 2027-09-13（43 周） | 一个人评审 = 项目白等 7 个月 |
| 评审人 | **2** | **2027-05-03（24 周）** | 当前假设，且**无余量** |
| 评审人 | 3 | 2027-03-18（17.4 周） | 边际收益最大的一档 |
| 评审人 | 4 | 2027-02-22（14 周） | 到波次串行下限，再加无效 |
| agent | 2 / 3 / 8 | 都是 2027-05-03 | **3 个就够**，8 个纯浪费（峰值占用 6/56 机日） |
| 板卡 | 1 / 2 / 4 / 8 | 都是 2027-05-03 | 模型上 1 块够；实际给 2–4 块留返工余量 |
| token 预算 | 50k / 100k / 200k 人日 | 生成 145/289/578 h | 200k 时 4 agent 也只要 6 天，仍不是瓶颈 |

**唯一能再省一个月的动作**：评审只做 G2 / G4 两次（G1/G3 只收 AI 生成的证据包，
人看 `run_ab.sh` + `diff_kernels` 的输出与 `perf-log.md`）→ 评审人日 192 → 约 80，
2 人 → 8 周，主线可到 **2027-02 中旬**。代价是 G3 阶段质量完全依赖门禁而不依赖人眼。

## 9. 瓶颈转移后的四条硬约束

1. **评审按"项目"排，不按"波次"排**。每周 2 个评审人满打满算审 4 个项目；
   小项目（D2/D3）攒成批走"快审窗口"，否则像 W3 那样被 W2 堵 7 周。
2. **agent 4 个、板卡 2–4 块就够，别加**。生成侧峰值只占 6/56 机日，板卡峰值 35/56；
   把钱花在评审产能上。
3. **一个项目绑一个 agent 会话，从头做到尾**。每工程上下文重建 50–150k token，
   换一次人就是一次重复开销；80.5M 预算里已含这份固定成本，换人就要再加。
4. **上游化（G5）不在算力模型内**：PR、reviewer 往返、CI 排队是 8–12 周日历时间，
   M-H 只能按日历排。

## 10. 这个模型最容易错在哪

| 失守点 | 表现 | 纠正 |
|---|---|---|
| 把 60 tok/s 当有效产出 | 按 5.18 M/天 估，得出"一周干完 48 项" | 按 100k/人日 的放大倍数算，别用裸 token |
| 忽略验证机时 | 认为写完就完事，排期只算生成 | 验证占 60%，且是墙钟，按板卡数排 |
| 忽略评审排队 | 只看"验证完"就宣布里程碑 | 里程碑按**末次评审**算（本文即如此） |
| 评审走过场 | 为赶日历，证据不看就签 | 一次错误基线会让下游全部返工，比分包更贵 |
| 用 qemu 当结论 | 按 qemu 加速比排期 | qemu 只证明功能，性能必须真机 |
| 频繁换 agent | 每波次重开会话 | 按项目绑定，上下文成本只付一次 |

## 11. 怎么用

```bash
python3 scripts/ai-capacity.py                       # 波次级：token / 机时 / 评审
python3 scripts/ai-plan.py                           # 项目级：日期 + agent + 板 + 评审（48 行）
python3 scripts/ai-plan.py --reviewers 3             # 加一个评审人看能省多久
python3 scripts/ai-plan.py --agents 4 --boards 2     # 瘦资源场景
python3 scripts/build-xlsx.py                         # 报表：AI 排期 / 项目排期 两个 sheet
```
