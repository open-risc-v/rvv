# 02 优先级判定规则

优先级回答一个问题：**在产能固定的前提下，下一个该做谁**。它不等于难度，也不等于工作量。
判定用规则，不用打分——打分会给 48 个项目制造虚假的精度。

## 1. 规则（按顺序命中，先命中先定档）

| 规则 | 条件 | 效果 |
|---|---|---|
| **R1 出货路径** | 在 ChromiumOS 出货镜像的运行路径上（浏览器渲染、媒体解码、图像编解码、TLS、压缩、启动） | 定 **P0** |
| **R2 基础库** | 通用发行版的高频依赖（被 ≥20 包传递依赖，或属安全/压缩/数学/编解码底座） | 至少 **P1** |
| **R3 杠杆** | 为其他包提供 SIMD 抽象或代码生成能力（Eigen/XNNPACK/Highway/SIMDe/fftw codelet） | 升一档 |
| **R4 已有上游 RVV** | 上游已合入 RVV 内核，或可被 `-march=rv64gcv` 自动向量化覆盖 | 降一档（工作量低，收益快） |
| **R5 停滞/死项目** | 上游 ≥2 年无实质提交，或仅测试/玩具用途 | 定 **P3** |
| **R6 验证不可行** | 无法建立确定性参照（无 CLI、无黄金数据、结果含随机/时间依赖） | 最多 **P2**，先补验证手段 |

P0 与 P1 都进主线波次；P2 进波次但可被 P0/P1 插单挤占；P3 只留档，不排产能。

## 2. 三档定义

| 档 | 定义 | 排期承诺 | 数量（本工程） |
|---|---|---|---|
| **P0** | 不做就不能出货，或不做则整机性能/功耗不达标 | 12 个月内必须 G4 | 13 |
| **P1** | 生态底座，做了整机收益明显，但可用标量路径顶住 | 18 个月内 G3 | 15 |
| **P2** | 有明确收益场景，但依赖下游先完成 | 按插单 | 13 |
| **P3** | 长尾/遗留/收益不足 | 不排产能 | 7 + 长尾 118 |

## 3. 三条反直觉结论

### 3.1 不要把"ISA 列最多"当优先级

`xlsx` 的列（NEON/SSE/SSE2/SSE3/SSE4/AVX/AVX2）只说明**上游做过多少种指令集路径**，
不说明这些路径在当前目标机上值多少钱。典型反例：

- `sci-libs/givaro`、`linbox`、`fflas-ffpack` 都横跨 5 列，但它们是**数学库的小众后端**，
  整机基本不跑 → P3。
- `media-libs/libjpeg-turbo` 只有 3 列，但它是每一次图像解码的必经之路 → P0。

**真正决定优先级的是"在目标机负载画像里的时间占比 × 用户可感知度"**，不是表格宽度。

### 3.2 上游已有 RVV 是"最高 ROI"，必须前置

实测（见 `data/upstream-probe.json`）上游已落 RVV 的关键包：

| 包 | 上游 RVV 现状 | 对本工程的含义 |
|---|---|---|
| `libjpeg-turbo` | 15 个 `simd/riscv64/*-rvv.c` | 只需补齐 upsample/huffman/12-bit + dispatch + 回归 |
| `libpng` | `riscv/filter_rvv_intrinsics.c` | filter 已覆盖，补 16-bit 与 interlaced 路径 |
| `zlib-ng` | `arch/riscv/`（adler32/chunkset/compare256/slide_hash/crc32_zbc） | 缺口在 `longest_match`（deflate 主循环） |
| `pixman` | `pixman-rvv.c` 部分 fast path | 快路径组合爆炸，需按"算子 × 格式"补矩阵 |
| `openssl` | 32 个 RISC-V 汇编（zkned/zvbb/zvkg/ghash/chacha） | 缺口 SHA-256/512、部分 bignum |
| `libgcrypt` | 26 个（chacha/poly1305/gcm/rijndael/sha1） | 缺口 sha256/sha512、mpi |
| `ffmpeg` | 151 个 RISC-V 文件 | 缺口 swscale、hevc、部分 dsp |
| `eigen` | `arch/RVV10/` 全后端 | 缺的是 GEMM packing 调优与 VLEN 无关性验证 |
| `vlc` / `ceph` | riscv 模块 / crc32c | 验证 + 少量缺口 |

这条规则的反面同样成立：**上游没有 RVV 且 SIMD 面巨大的包（libvpx/hyperscan/x264）ROI 最低**，
不该放在第一个波次，但也不能不做——它们是"必须付的账"，只是要按"关键内核子集"分期付。

### 3.3 表里的 167 个包，60% 是 `media-libs/media-*`

按 Gentoo 类别统计（见 `data/inventory.csv` 的 `category` 列），媒体类占绝大多数。
这不是巧合：音视频/图像是 x86 SIMD 历史投入最重的地方。因此**波次设计必须按"媒体族"
而不是按"包"来切**，否则会出现 6 个人同时改 6 个 ffmpeg 依赖库、互相 rebase 的场面。

## 4. 优先级到波次的映射

| 档 | 波次 | 理由 |
|---|---|---|
| P0 且上游已有 RVV | W1 | 最快出可见收益，同时把 A/B 与真机链路跑通 |
| P0 编解码 | W2 | 收益最大、工作量最大，需要整块产能 |
| P0 音频/实时通信 | W3 | WebRTC 链路，实时约束强，需专门的真机时延测试 |
| P1 安全/压缩/存储 | W4 | 与媒体解耦，可并行 |
| P1 数学/科学计算 | W5 | 依赖 `eigen` 与工具链质量，前置是 W1 的工具链矩阵 |
| P0 平台（chromium/node） | W6 | 只做"集成 + 缺口"，不做全量重写；依赖前面所有上游成果 |
| P3 长尾 | W7 | 插单 |

## 5. 优先级复核触发条件

出现以下任一情况，重判该包档位（在 `data/status.csv` 记一行）：

1. 真机剖析显示该包在目标负载里占比 <1%（降档）；
2. 上游在近 6 个月合入 RVV 内核（升档，转"集成 + 缺口"模式）；
3. 目标机的 ISA 扩展变化（如获得 `zvbb/zvkned` 支持，密码类升档）；
4. 出现新的出货形态（如新增视频通话，`libvpx`/`openh264` 升档）。
