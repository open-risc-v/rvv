# 01 难度分级与工作量估算模型

## 1. 难度 D1–D5

难度只看**移植这件事本身的结构性阻力**，不看包的知名度、不看工作量大小。

| 级 | 名称 | 判定特征（满足任一即可） | 典型例子 |
|---|---|---|---|
| **D1** | 接口级 | 无自有 SIMD，或只有 1–2 个可被编译器自动向量化的循环；工作主要是构建门控与打包 | `common-assets`、`uchardet`、`ramspeed` |
| **D2** | 内核级（有参照） | 已有 per-arch **C intrinsics** 实现（NEON/SSE 的 `.c` 而非 `.asm`）可直接对照改写；运算以逐元素/点积为主，无强顺序依赖 | `libpng` 的 filter、`flac`、`libsoundtouch`、`kissfft` |
| **D3** | 内核级（自建） | 无现成 C intrinsics 参照，或需要自建 SIMD 抽象层；存在 pack/unpack、跨 lane 洗牌、水平归约、饱和管线、多 bpp/多格式分支 | `libwebp`、`zimg`、`openexr`、`gdal` 重采样 |
| **D4** | 汇编级 / 严格契约 | 核心路径是**手写汇编**（x86 `.asm` / NEON `.S`），需按语义重写；或存在 bit-exact / 常数时间 / 码流兼容等硬契约 | `openssl` 缺口、`libvpx`、`openh264`、`nettle`、`crypto++` |
| **D5** | 架构级 | 需重构数据布局或算法骨架（GEMM blocking/FFT codelet/正则匹配/BVH 遍历），且必须 VLEN 无关；大规模回归面 | `fftw`、`tensorflow`、`hyperscan`、`embree`、`gromacs`、`chromium` |

**单内核成本**（含编码 + 自测 + 差分测试，不含等 CI）：

| 级别 | 单内核人日 | 说明 |
|---|---|---|
| D1 | 0.2 | 主要是构建/开关 |
| D2 | 1.0 | 一对一映射，坑集中在 lane 语义 |
| D3 | 2.0 | 需自己设计 lane 布局与归约顺序 |
| D4 | 3.5 | 汇编语义复原 + 位精确论证 |
| D5 | 6.0+ | 往往是"先改结构再写内核" |

> 单内核成本不是线性叠加：同一包内第 2 个内核起成本降 20–30%（宏、布局、测试夹具复用）。
> 估算时用 `n_k` 的首个全价、其余按 0.8 折算。

## 2. 工作量模型

```
工作量(人日) = S + Σ_k [ c(D) × (1 + 0.8 × (n_k - 1)) ] × V + U
```

| 项 | 含义 | 取值 |
|---|---|---|
| `S` 启动成本 | 骨架、构建改造、A/B 工具、数据集、dispatch | 2（抽象层现成）/ 4（自建 A/B）/ 8（多构建系统 / 多 target / 巨大仓库） |
| `n_k` | 需移植的内核数（以"函数/内核表项"为单位，不是文件数） | 由 `upstream-probe.json` 的 SIMD 文件数约束：**内核数 ≈ SIMD 源文件数的 2–4 倍**（一个文件常含多个内核） |
| `c(D)` | 单内核成本，见上表 | — |
| `V` 验证系数 | 容差验证 1.0 / bit-exact 1.5 / bit-exact + 格式或常数时间 2.0 | 见 `docs/06-acceptance.md` |
| `U` 上游化 | PR 往返、风格对齐、CI 适配 | 工作量 × 10–20% |

**为什么 `V` 必须显式**：`libspeex-rvv` 的实际数据是"21 个内核 / 约 12 个有效工作日"，
即 1.7 内核/人日；但该项目的**时间分布**是：写内核 ≈ 40%，验证与排障 ≈ 60%。
把验证折进单价（`c(D)`）会把 bit-exact 项目低估 40%–100%，所以拆开算。

## 3. 锚点校准

| 锚点 | 实测/已知 | 用来校准什么 |
|---|---|---|
| `libspeex-rvv` | 21 个 RVV 覆盖点、29 轮、单人约 12 天；每内核配差分测试 | D2/D3 单价、`V=1.5` 的现实值、`S=2`（模板现成） |
| `libjpeg-turbo` | 上游已有 15 个 `simd/riscv64/*-rvv.c`，x86 侧 89 个、NEON 侧 23 个 SIMD 文件 | "上游已有 RVV" 的项目不是从零，工作量≈缺口 + 集成（3–5 倍差距） |
| `ffmpeg` | 151 个 RISC-V 文件（`libavcodec/riscv/*.S` 为主），x86 侧仅 55 个（大量在 `.asm` 生成器里） | 汇编类包的真实"面"不能只看路径计数；`ffmpeg` 的缺口在 swscale 与部分 codec |
| `pixman` | 22 个 SIMD 路径文件，其中 5 个 RISC-V（`pixman-rvv.c`） | 快路径组合爆炸（算子 × 格式 × bpp）→ D4 而非 D3 |
| `eigen` | 已有 `Eigen/src/Core/arch/RVV10/` 全后端 | "上游已有" ≠ 已优化好：仍要 GEMM blocking 调优与 VLEN 无关性验证 |
| `fftw3` | 108 个 SIMD 路径文件，0 个 RISC-V | codelet 生成器 + SIMD 抽象层是工作量主体（D5） |

## 4. 置信度

- **区间宽度**：核心 48 个项目的工作量是**低–高区间**，规划值取 `(低+高)/2 × 1.15`。
  经验上真实值落在区间的概率约 60–70%，落在区间外的主要原因是"上游大版本变更"与
  "工具链代码生成质量问题"（例如 gcc 对某些 intrinsics 形态生成极差代码，需要绕路重写）。
- **长尾 118 个项目**只给粗档（S ≤5 / M 6–15 / L 16–40），不给点估计；理由是单包收益
  不足以支撑精细化评估的成本，插单时再按 D 级重估。
- **不把"没核实"写成"没有"**：`upstream-probe.json` 里 `rvv_status` 为 `unknown` 的条目
  （如 libaom、mpg123、x265 克隆失败），一律标注待核实，估算按"无 RVV"上限给。

## 5. 常见误判（本工程要主动规避）

1. **按文件数估工作量**：`chromium` 有 3410 个"x86 SIMD 路径"文件，实际大部分是
   third_party 里的重复（libpng/zlib/icu），真工作量在 Skia/V8/ANGLE 三处。文件计数只做量级约束。
2. **忽略 dispatch 与构建**：RVV 内核必须有编译门控（`-march`、`__riscv_v_intrinsic` 版本轴、
   运行期 hwcap/probe）。这部分在 167 个包里是重复劳动，**必须由 W0 的公共方案收口**，
   否则每个包多花 1–2 人日。
3. **拿 qemu 数据当加速比**：qemu（TCG）只能做功能回归，性能数字必须来自真机。
4. **把"能跑通"当"移植完成"**：门禁 G4 要求覆盖度与收敛判定，缺一个都不算完。
